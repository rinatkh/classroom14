# Как не нужно работать с PostgreSQL

Все примеры ниже нужны для обсуждения. Не запускайте опасные варианты на важных
данных.

## 1. UPDATE или DELETE без WHERE

```sql
-- ПЛОХО: изменит каждую строку таблицы.
UPDATE tasks SET done = true;

-- ПЛОХО: удалит каждую строку таблицы.
DELETE FROM tasks;
```

Сначала сформулируйте, какие строки нужны, выполните соответствующий `SELECT`,
и только затем переносите условие в `UPDATE` или `DELETE`.

## 2. Склеивать SQL со значением пользователя

```go
// ПЛОХО: title меняет текст SQL и может привести к SQL injection.
query := "SELECT id FROM tasks WHERE title = '" + title + "'"

// ХОРОШО: текст запроса и данные передаются отдельно.
row := db.QueryRow(ctx, "SELECT id FROM tasks WHERE title = $1", title)
```

## 3. Забыть закрыть Rows

```go
// ПЛОХО: соединение может остаться занятым до сборки мусора.
rows, err := db.Query(ctx, query)
if err != nil {
	return err
}
for rows.Next() {
	// читаем строки
}
// rows.Close и rows.Err отсутствуют.
```

```go
// ХОРОШО: закрываем Rows сразу после успешного Query и проверяем ошибку цикла.
rows, err := db.Query(ctx, query)
if err != nil {
	return err
}
defer rows.Close()

for rows.Next() {
	// читаем строки
}
if err := rows.Err(); err != nil {
	return err
}
```

Без `Close` соединение может дольше оставаться занятым. После цикла также нужно
проверять `rows.Err()`.

## 4. Считать любую ошибку «объект не найден»

`pgx.ErrNoRows` означает отсутствие строки. Ошибка соединения или синтаксиса SQL
означает проблему сервера. Первая превращается в `404`, вторая — в `500` и лог.

## 5. Добавлять индекс на каждую колонку

Индекс ускоряет подходящие чтения, но занимает место и требует обновления при
`INSERT`, `UPDATE`, `DELETE`. Сначала нужен реальный запрос, затем измерение через
`EXPLAIN (ANALYZE, BUFFERS)`, и только затем решение об индексе.

## 6. Хранить пароль в репозитории

Настоящий `DATABASE_URL` не должен попадать в Git. В репозитории остаётся только
`.env.example` с учебным шаблоном.

## 7. Использовать trigger для всей бизнес-логики

Trigger удобен для небольшого правила, одинакового для всех способов обновления,
например `updated_at`. Если спрятать в triggers сложные решения приложения, путь
изменения данных станет трудно читать и тестировать.
